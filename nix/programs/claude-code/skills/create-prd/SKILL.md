# create-prd: PRD作成・更新ヒアリングスキル

PRD は一度で書き切らず、6つの段階を経て解像度を上げていく。このスキルは、PRD の現在の段階を定め、次の段階へ進むために決めるべき材料を grilling で聞き取り、ユーザーの承認を得てから tanteki に執筆または更新を渡す。このスキルは材料集めだけを行う。

PRD は「何を作るか」より先に「なぜそれが重要か」に答え、意思決定に伴うトレードオフを隠さずに残す。

## PRD の段階

| 段階 | 領域 | 何が起きているか | PRD に加える項目 | 重要な問い | よくある失敗 |
|---|---|---|---|---|---|
| 1. 出発点 | 課題 | 探る価値のある課題を見つける | 問題と根拠（仮説でよい）、なぜ今か、対象となる利用者、仮説、未解決の問い | これは時間をかけるべきことか | 検証不足のまま解決策に飛びつく |
| 2. ディスカバリー | 課題 | 調査やデータで、問題が重要かを検証する | 問題と根拠（検証済み）、提供する価値、出典 | この問題は解決する価値があるか | 何も作っていない不安から検証を急ぐ |
| 3. 定義 | 課題 | 制約、トレードオフ、対象外を明確にする | 対象外、制約とトレードオフ、成功条件、計測と学習の計画 | 何を解決し、何を解決しないか | 範囲を絞らず全部を解決しようとする |
| 4. 設計 | 解決策 | 解決策を複数検討し、比べる | 解決案とトレードオフ、業務要求・機能要求 | 解く方法は何か、それぞれの利点と欠点は何か | 最初に思いついた案に固執する |
| 5. デリバリー | 解決策 | 最終決定し、実装に渡す | 受入条件、成功条件の測定方法、展開計画、全項目の確定（`TBD` なし） | 何を作り、成功をどう測るかを全員が理解しているか | 指標があいまいなまま開発を進める |
| 6. 運用 | 解決策 | リリース後に利用状況と効果を測る | 結果と学び、仮説との比較、次への示唆 | 何を学び、次にどう活かすか | リリースで PRD の役目が終わったと考える |

各段階は前の段階の項目を前提とする。課題領域（段階1〜3）から解決策領域（段階4〜6）への移行が最も重要な境界である。課題領域が合意されるまで解決策領域の項目を聞かない。

## 手順

### 1. 資料を確認する

ユーザーが示した資料、既存の PRD、これまでの会話だけを読む。リポジトリを自発的に探索しない。

既存の PRD を更新する場合は、その PRD を読み、どの項目が確定しているかを把握する。

### 2. 段階を定める

資料から PRD の現在の段階を判定し、今回到達させる段階を推奨回答として示す。新規作成では段階1、既存 PRD の更新では次の段階を既定とする。ユーザーが異なる段階を指定した場合はそれに従う。

到達させる段階より後の段階の項目は聞かない。それらは `TBD` ではなく未着手として扱う。理解が足りない段階で細部まで決めようとしない。

### 3. 読者を確認する

PRD の読者は PdM、開発者、QA担当、CS担当である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 4. grilling を領域ごとに行う

到達させる段階までの未確定の項目を、課題領域と解決策領域に分け、領域ごとに `Skill` ツールで `grilling` を呼ぶ。確定済みの項目は飛ばし、飛ばしたことをユーザーに伝える。

| 領域 | 項目 | 何のために聞くか |
|---|---|---|
| 課題 | 問題と根拠 | 要求が必要な理由と、なぜ今取り組むかを支える |
| | 対象となる利用者 | 誰の問題かを定める |
| | 仮説 | 何が起きると見込むかを残し、運用の段階で結果と比べる |
| | 提供する価値 | 関係者が何を得るかを示す |
| | 対象外 | 要求の適用範囲を限る |
| | 制約とトレードオフ | 何を得るために何を諦めるかを明示する |
| | 成功条件 | 要求が満たされたかを判断する基準 |
| | 計測と学習の計画 | リリース後に何を測り、何を学ぶかを最初に決めておく |
| 解決策 | 解決案とトレードオフ | 検討した複数の案と、選んだ理由を残す |
| | 業務要求・機能要求 | 選んだ案が、どの振る舞いで問題を解決するか |
| | 受入条件 | 受け入れを判断する基準 |
| | 成功条件の測定方法 | 成功条件を何でどう測るかを確定する |
| | 展開計画 | 誰に、どの順で、どう提供するか |
| | 結果と学び | 成功条件と仮説に対する実績、次への示唆 |
| 両方 | 未解決の問い | 次の段階へ進む前に答えるべき問いを残す |
| | 出典 | 各主張の根拠となる原資料 |

各領域の grilling には、その領域の項目と到達させる段階を論点として渡し、確定済みの項目を前提として添える。各項目について、到達させる段階の重要な問いに答えられるかを詰め、よくある失敗に当たっていれば指摘する。

解決策領域では、案が一つしか出ない場合に、少なくとも一つの代替案と比べることを求める。解決案の比較は利用者から見える振る舞いの水準にとどめ、技術的な実現方式の比較は ADR や Design Doc に委ねる。

領域の終わりに、その領域の結論を短くまとめて示し、修正がないことを確かめてから次へ進む。これは領域の結論の確認であり、執筆の承認ではない。課題領域の終わりでは、正しい課題を解こうとしているか、課題の文を確定させる前に開発やデザインなどの関係者の意見を集めたかを確かめる。集めていない場合は未解決の問いに加える。解決策領域で課題領域の結論と矛盾が見つかった場合は、課題領域に戻って詰め直す。

項目はいずれもユーザーが決めることであり、調べて埋める事実ではない。grilling は事実の調査をサブエージェントに任せるよう求めるが、このスキルでは調査を手順1の範囲にとどめ、サブエージェントを起動しない。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。回答にない事実、数値、条件を補わない。

ユーザーが決まっていないと答えた項目は、考えさせ続けずに `TBD` とし、未解決の問いに加えて次へ進む。段階5へ到達させる場合に `TBD` が残るときは、段階4にとどめることを推奨回答として示す。

### 5. 材料一覧を提示して合意を取る

到達させる段階、全項目の一覧（確定、`TBD`、未着手の別）、`TBD` の件数、未解決の問いを示す。この内容で PRD を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順6へ進む。

### 6. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料と到達させる段階を渡して PRD を執筆させる。PRD には現在の段階と未解決の問いを記載させる。未着手の項目は PRD に含めない。

既存の PRD を更新する場合は、同じファイルを更新させ、新しいファイルを作らない。前の段階で確定した記述を、ユーザーの承認なしに書き換えさせない。運用の段階では、結果と学びを追記し、当初の仮説や成功条件を消さずに比べられる形で残させる。

PRD の保存先は、どのリポジトリでもリポジトリルートの `docs/prd/` に固定する。保存先をユーザーに問わず、tanteki にも渡す。

新規の PRD のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存 PRD の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは PRD の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_environment-setup.md`

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- 技術的な実現方式の選択（Design Doc、ADR の領分）
- 作業の分担と進捗（計画、チケットの領分）
- リリース後の計測そのもの（結果は数値や資料としてユーザーから受け取る）
