# create-prd: PRD作成ヒアリングスキル

PRD の材料を grilling で三段階に分けて聞き取り、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

## 手順

### 1. 資料を確認する

ユーザーが示した資料と、これまでの会話だけを読む。リポジトリを自発的に探索しない。既存の記述から埋まる項目は、手順3で飛ばす。

### 2. 読者を確認する

PRD の読者は PdM、開発者、QA担当、CS担当である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 3. grilling を三段階で行う

8項目を次の三段階に分け、段階ごとに `Skill` ツールで `grilling` を呼ぶ。後の段階は前の段階の結論に依存するため、段階の順序を入れ替えず、前の段階が確定するまで次の段階へ進まない。手順1で埋まっている項目は飛ばし、飛ばしたことをユーザーに伝える。

| 段階 | 狙い | # | 項目 | 何のために聞くか |
|---|---|---|---|---|
| 1. 問題 | 誰の何を解決するかを定める | 1 | 問題と根拠 | 要求が必要な理由を支える |
| | | 2 | 対象となる利用者 | 誰の問題かを定める |
| | | 3 | 提供する価値 | 関係者が何を得るかを示す |
| 2. 要求 | 解決する振る舞いと範囲を定める | 4 | 業務要求・機能要求 | どの振る舞いで問題を解決するか |
| | | 5 | 対象外 | 要求の適用範囲を限る |
| 3. 検証 | 満たしたと判断する基準を定める | 6 | 成功条件 | 要求が満たされたかを測定する基準 |
| | | 7 | 受入条件 | 受け入れを判断する基準 |
| | | 8 | 出典 | 各主張の根拠となる原資料 |

各段階の grilling には、その段階の項目だけを論点として渡し、前の段階で確定した結論を前提として添える。段階の終わりに、その段階の結論を短くまとめて示し、修正がないことを確かめてから次の段階へ進む。これは段階の結論の確認であり、執筆の承認ではない。後の段階で前の段階の結論と矛盾が見つかった場合は、該当する段階に戻って詰め直す。

8項目はいずれもユーザーが決めることであり、調べて埋める事実ではない。grilling は事実の調査をサブエージェントに任せるよう求めるが、このスキルでは調査を手順1の範囲にとどめ、サブエージェントを起動しない。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。回答にない事実、数値、条件を補わない。

ユーザーが決まっていないと答えた項目は、考えさせ続けずに `TBD` として次へ進む。

### 4. 材料一覧を提示して合意を取る

三段階を終えたら、全8項目を段階ごとに一覧で示し、`TBD` の件数を併記する。この内容で PRD を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順5へ進む。

### 5. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料を渡して PRD を執筆させる。

PRD のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先にある既存 PRD の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは PRD の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_setup.md`

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- PRD ファイルの保存先ディレクトリ
- 要求を満たす実現方式の選択（Design Doc、ADR の領分）
- 作業の分担と進捗（計画、チケットの領分）
