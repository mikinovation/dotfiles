# code-to-prd: コードからのPRD逆生成スキル

対象範囲のコードを調べて PRD の材料を集め、コードから確定できない項目を grilling で詰め、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

## 手順

### 1. 対象範囲を一つに絞る

PRD にする機能と、それを実装しているディレクトリ、エントリポイント、画面、API のいずれかをユーザーに確認する。範囲が複数の機能にまたがる場合は、どれを PRD にするかをユーザーに選ばせる。リポジトリ全体を一つの PRD にしない。

### 2. 読者を確認する

PRD の読者は PdM、開発者、QA担当、CS担当である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 3. コードを調べる

手順1で決めた範囲について、次の情報源を読む。範囲外へは、範囲内のコードが呼び出す先を確かめる場合に限って広げる。

| 情報源 | 抽出するもの |
|---|---|
| ルーティング、画面、CLI、公開 API | 利用者が触れる入口と操作 |
| 入力検証、権限判定、エラー処理 | 操作の前提条件、制約、失敗時の振る舞い |
| テスト（単体、結合、E2E） | 期待される振る舞いと境界条件 |
| README、ドキュメント、コメント | 機能の目的と対象利用者の記述 |
| 設定値、フィーチャーフラグ | 振る舞いが切り替わる条件 |
| コミット履歴、関連する Issue や PR | 機能が追加された理由と経緯 |

範囲が広く、互いに独立した複数の領域を読む必要がある場合に限り、領域ごとにサブエージェントへ調査を分担させる。

抽出した振る舞いは、利用者から観察できる形に言い換える。関数名、クラス名、テーブル名、ライブラリ名などの実装の詳細は材料に含めない。ただし出典には、根拠となるファイルと行番号を残す。

### 4. 項目ごとに根拠の種類を分類する

8項目それぞれについて、手順3の結果を次の三種類に分類する。

| 分類 | 意味 | 扱い |
|---|---|---|
| 確認済み | コード、テスト、ドキュメントに直接の記述がある | 出典を添えて材料に入れる |
| 推測 | 間接的な手がかりから導いた | 推測であることと根拠を示し、手順5で確かめる |
| 不明 | 手がかりがない | 手順5で聞く |

項目ごとの主な情報源は次のとおりである。

| 段階 | # | 項目 | 主な情報源 |
|---|---|---|---|
| 1. 問題 | 1 | 問題と根拠 | ドキュメント、コミット履歴、Issue。多くは不明になる |
| | 2 | 対象となる利用者 | 権限判定、画面の文言、ドキュメント |
| | 3 | 提供する価値 | ドキュメント。多くは推測か不明になる |
| 2. 要求 | 4 | 業務要求・機能要求 | 入口、処理、テスト |
| | 5 | 対象外 | ドキュメントの明記、明示的に拒否する処理 |
| 3. 検証 | 6 | 成功条件 | 計測イベント、メトリクス。多くは不明になる |
| | 7 | 受入条件 | テスト、入力検証 |
| | 8 | 出典 | 手順3で読んだファイル、履歴、Issue |

次の二点を守る。

- 実装されていないことを「対象外」と判断しない。未実装と対象外の区別はユーザーに確かめる。
- コードの振る舞いと、テスト、ドキュメント、コメントの記述が食い違う場合は、どちらかを正として採らず、食い違いとして記録して手順5で確かめる。バグの可能性がある振る舞いを要求として固定しない。

### 5. grilling を三段階で行う

手順4の表の三段階ごとに、`Skill` ツールで `grilling` を呼ぶ。後の段階は前の段階の結論に依存するため、段階の順序を入れ替えず、前の段階が確定するまで次の段階へ進まない。

各段階の grilling には、その段階の「推測」と「不明」の項目、および手順4で記録した食い違いを論点として渡し、「確認済み」の項目と前の段階で確定した結論を前提として添える。「確認済み」の項目は論点にせず、根拠とともに提示して誤りがあれば修正を求める。全項目が「確認済み」の段階は grilling を呼ばず、結論の提示だけで次の段階へ進む。

事実の調査は手順3で済ませているため、grilling の途中でサブエージェントを起動しない。ユーザーの回答で新たに確かめるべき箇所が出た場合は、自分でコードを読んで確かめる。

推測は提案であることを明示して示す。ユーザーが承認するまで材料に書き込まない。コードにも回答にもない事実、数値、条件を補わない。

段階の終わりに、その段階の結論を短くまとめて示し、修正がないことを確かめてから次の段階へ進む。これは段階の結論の確認であり、執筆の承認ではない。後の段階で前の段階の結論と矛盾が見つかった場合は、該当する段階に戻って詰め直す。

ユーザーが決まっていない、わからないと答えた項目は、考えさせ続けずに `TBD` として次へ進む。

### 6. 材料一覧を提示して合意を取る

三段階を終えたら、全8項目を段階ごとに一覧で示す。各項目に根拠の種類（コードで確認、ユーザー回答、`TBD`）を併記し、`TBD` の件数と未解決の食い違いの件数を添える。この内容で PRD を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順7へ進む。

### 7. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料を渡して PRD を執筆させる。材料には、この PRD が既存の実装から起こしたものであることと、調査の基準にしたコミットを含める。

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- PRD ファイルの保存先
- 実装の構成、データの流れ、技術選定の記録（Design Doc、ADR の領分）
- 見つかったバグの修正、リファクタリング
- 作業の分担と進捗（計画、チケットの領分）
