# code-to-prd: コードからのPRD逆生成スキル

PRD は6つの段階を経て解像度を上げていく。既存のコードから起こす PRD は、すでに実装された振る舞いを扱うため、段階5（デリバリー）または段階6（運用）を到達点とする。このスキルは、その段階までの材料を grilling で詰め、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

PRD は「何を作ったか」より先に「なぜそれが重要か」に答え、意思決定に伴うトレードオフを隠さずに残す。コードから読めるのは「何を作ったか」だけであり、「なぜ」はユーザーに確かめる。

## PRD の段階

| 段階 | 領域 | PRD に加える項目 | 重要な問い | よくある失敗 |
|---|---|---|---|---|
| 1. 出発点 | 課題 | 問題と根拠、なぜ今か、対象となる利用者、仮説、未解決の問い | これは時間をかけるべきことか | 検証不足のまま解決策に飛びつく |
| 2. ディスカバリー | 課題 | 問題と根拠（検証済み）、提供する価値、出典 | この問題は解決する価値があるか | 何も作っていない不安から検証を急ぐ |
| 3. 定義 | 課題 | 対象外、制約とトレードオフ、成功条件、計測と学習の計画 | 何を解決し、何を解決しないか | 範囲を絞らず全部を解決しようとする |
| 4. 設計 | 解決策 | 解決案とトレードオフ、業務要求・機能要求 | 解く方法は何か、それぞれの利点と欠点は何か | 最初に思いついた案に固執する |
| 5. デリバリー | 解決策 | 受入条件、成功条件の測定方法、展開計画 | 何を作り、成功をどう測るかを全員が理解しているか | 指標があいまいなまま開発を進める |
| 6. 運用 | 解決策 | 結果と学び、仮説との比較、次への示唆 | 何を学び、次にどう活かすか | リリースで PRD の役目が終わったと考える |

逆生成では、コードが解決策領域の事実を先に示すため、課題領域を飛ばして実装の説明だけの PRD になりやすい。課題領域が合意されるまで解決策領域の項目を確定させない。

## 手順

### 1. 対象範囲を一つに絞る

PRD にする機能と、それを実装しているディレクトリ、エントリポイント、画面、API のいずれかをユーザーに確認する。範囲が複数の機能にまたがる場合は、どれを PRD にするかをユーザーに選ばせる。リポジトリ全体を一つの PRD にしない。

対象範囲を決めた時点のコミットを記録し、以降の調査はこのコミットを基準にする。

### 2. 段階を定める

到達させる段階を推奨回答として示す。既定は段階5とし、ユーザーがリリース後の利用状況や効果の資料を持っている場合は段階6とする。

### 3. 読者を確認する

PRD の読者は PdM、開発者、QA担当、CS担当である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 4. grilling を領域ごとに行う

到達させる段階までの項目を課題領域と解決策領域に分け、領域ごとに `Skill` ツールで `grilling` を呼ぶ。課題領域が確定するまで解決策領域へ進まない。

| 領域 | 項目 | コード上の主な手がかり |
|---|---|---|
| 課題 | 問題と根拠 | ドキュメント、コミット履歴、Issue |
| | 対象となる利用者 | 権限判定、画面の文言、ドキュメント |
| | 仮説 | Issue、ドキュメント |
| | 提供する価値 | ドキュメント |
| | 対象外 | ドキュメントの明記、明示的に拒否する処理 |
| | 制約とトレードオフ | ドキュメント、上限や制限を課す処理 |
| | 成功条件 | 計測イベント、メトリクス |
| | 計測と学習の計画 | 計測イベント、メトリクス |
| 解決策 | 解決案とトレードオフ | Issue、コミット履歴、ADR |
| | 業務要求・機能要求 | ルーティング、画面、CLI、公開 API、テスト |
| | 受入条件 | テスト、入力検証、エラー処理 |
| | 成功条件の測定方法 | 計測イベント、メトリクス |
| | 展開計画 | 公開範囲を切り替える設定 |
| | 結果と学び | なし（ユーザーが示す資料だけ） |
| 両方 | 未解決の問い | なし（grilling の結果） |
| | 出典 | Issue、ユーザー回答（コードは出典にしない） |

各領域の grilling には、その領域の項目、手順1で決めた対象範囲、到達させる段階、確定済みの項目を渡す。各項目について、その項目が属する段階の重要な問いに答えられるかを詰め、よくある失敗に当たっていれば指摘する。

grilling は、環境を調べてわかる事実は調べて埋め、決定はユーザーに委ねる。このスキルでは、この区別を次のように当てはめる。

- 事実: コードが現在どう振る舞うか。対象範囲のコード、テスト、ドキュメント、履歴を読んで埋める。根拠のファイルと行番号は材料一覧で示すが、PRD には含めない。調べる範囲は対象範囲と、そこから呼び出される先に限る。
- 決定: その振る舞いが意図した要求か、なぜ必要か、何をもって成功とするか、何を得るために何を諦めたか。コードから推測できても事実として扱わず、推奨回答としてユーザーに問う。

調べた振る舞いは、利用者から観察できる形に言い換えて材料に入れる。関数名、クラス名、テーブル名、ライブラリ名などの実装の詳細は材料に含めない。コマンド名、ファイル名、設定値、処理の手順など、要求をどう実現しているか（how）も材料に含めない。解決案の比較は利用者から見える振る舞いの水準にとどめ、技術的な実現方式の比較は ADR や Design Doc に委ねる。

PRD はコードより上位の文書であり、コードが PRD に従う。PRD からリポジトリのコード、ファイル、コミットを参照しない。

次の点は事実ではなく決定として、ユーザーに問う。

- 実装されていない振る舞いを、対象外として明記するか、PRD から省くか。
- コードの振る舞いと、テスト、ドキュメント、コメントの記述が食い違う場合に、どちらが意図した要求か。バグの可能性がある振る舞いを、確かめずに要求として固定しない。
- 計測の仕組みが見つからない場合に、成功条件をどう判断するか。

PRD には、現在実装されている振る舞いだけを含める。実装されていない振る舞いを、要求、成功条件、受入条件に入れない。

課題領域の終わりに、その結論を短くまとめて示し、正しい課題を記述できているかを確かめてから解決策領域へ進む。解決策領域の終わりにも結論を示して確かめる。これは領域の結論の確認であり、執筆の承認ではない。解決策領域で課題領域の結論と矛盾が見つかった場合は、課題領域に戻って詰め直す。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。コードとユーザーの回答のどちらにもない事実、数値、条件を補わない。

ユーザーが決まっていない、わからないと答えた項目は、考えさせ続けずに `TBD` とし、未解決の問いに加えて次へ進む。なぜ今か、仮説、解決案とトレードオフのような過去の経緯は、記録もユーザーの記憶もなければ `TBD` ではなく記録なしとし、段階の判定に含めない。それ以外の項目に `TBD` が残る場合は、到達させる段階を下げることを推奨回答として示す。

### 5. 材料一覧を提示して合意を取る

到達させる段階と、全項目を領域ごとに一覧で示す。各項目に根拠の種類（コードで確認、ユーザー回答、`TBD`、記録なし）を併記し、`TBD` の件数と未解決の問いを添える。この内容で PRD を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順6へ進む。

### 6. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料と到達させる段階を渡して PRD を執筆させる。PRD には現在の段階と未解決の問いを記載させる。記録なしの項目は PRD に含めない。材料には、リポジトリのコード、ファイル、コミットへの参照と、実現方式（how）を含めない。

PRD の保存先は、どのリポジトリでもリポジトリルートの `docs/prd/` に固定する。保存先をユーザーに問わず、tanteki にも渡す。

PRD のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存 PRD の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは PRD の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_environment-setup.md`

作成後に PRD を次の段階へ進める更新は create-prd で行う。

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- 実装の構成、データの流れ、技術選定の記録（Design Doc、ADR の領分）
- 見つかったバグの修正、リファクタリング
- 作業の分担と進捗（計画、チケットの領分）
- リリース後の計測そのもの（結果は数値や資料としてユーザーから受け取る）
