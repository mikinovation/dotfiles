# code-to-prd: コードからのPRD逆生成スキル

PRD の材料を grilling で三段階に分けて詰め、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

## 手順

### 1. 対象範囲を一つに絞る

PRD にする機能と、それを実装しているディレクトリ、エントリポイント、画面、API のいずれかをユーザーに確認する。範囲が複数の機能にまたがる場合は、どれを PRD にするかをユーザーに選ばせる。リポジトリ全体を一つの PRD にしない。

対象範囲を決めた時点のコミットを記録し、以降の調査はこのコミットを基準にする。

### 2. 読者を確認する

PRD の読者は PdM、開発者、QA担当、CS担当である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 3. grilling を三段階で行う

8項目を次の三段階に分け、段階ごとに `Skill` ツールで `grilling` を呼ぶ。後の段階は前の段階の結論に依存するため、段階の順序を入れ替えず、前の段階が確定するまで次の段階へ進まない。

| 段階 | 狙い | # | 項目 | コード上の主な手がかり |
|---|---|---|---|---|
| 1. 問題 | 誰の何を解決するかを定める | 1 | 問題と根拠 | ドキュメント、コミット履歴、Issue |
| | | 2 | 対象となる利用者 | 権限判定、画面の文言、ドキュメント |
| | | 3 | 提供する価値 | ドキュメント |
| 2. 要求 | 解決する振る舞いと範囲を定める | 4 | 業務要求・機能要求 | ルーティング、画面、CLI、公開 API、テスト |
| | | 5 | 対象外 | ドキュメントの明記、明示的に拒否する処理 |
| 3. 検証 | 満たしたと判断する基準を定める | 6 | 成功条件 | 計測イベント、メトリクス |
| | | 7 | 受入条件 | テスト、入力検証、エラー処理 |
| | | 8 | 出典 | Issue、ユーザー回答（コードは出典にしない） |

各段階の grilling には、その段階の項目、手順1で決めた対象範囲、前の段階で確定した結論を渡す。

grilling は、環境を調べてわかる事実は調べて埋め、決定はユーザーに委ねる。このスキルでは、この区別を次のように当てはめる。

- 事実: コードが現在どう振る舞うか。対象範囲のコード、テスト、ドキュメント、履歴を読んで埋める。根拠のファイルと行番号は材料一覧で示すが、PRD には含めない。調べる範囲は対象範囲と、そこから呼び出される先に限る。
- 決定: その振る舞いが意図した要求か、なぜ必要か、何をもって成功とするか。コードから推測できても事実として扱わず、推奨回答としてユーザーに問う。

調べた振る舞いは、利用者から観察できる形に言い換えて材料に入れる。関数名、クラス名、テーブル名、ライブラリ名などの実装の詳細は材料に含めない。コマンド名、ファイル名、設定値、処理の手順など、要求をどう実現しているか（how）も材料に含めない。

PRD はコードより上位の文書であり、コードが PRD に従う。PRD からリポジトリのコード、ファイル、コミットを参照しない。

次の二点は事実ではなく決定として、ユーザーに問う。

- 実装されていない振る舞いを、対象外として明記するか、PRD から省くか。
- コードの振る舞いと、テスト、ドキュメント、コメントの記述が食い違う場合に、どちらが意図した要求か。バグの可能性がある振る舞いを、確かめずに要求として固定しない。

PRD には、現在実装されている振る舞いだけを含める。実装されていない振る舞いを、要求、成功条件、受入条件に入れない。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。コードとユーザーの回答のどちらにもない事実、数値、条件を補わない。

段階の終わりに、その段階の結論を短くまとめて示し、修正がないことを確かめてから次の段階へ進む。これは段階の結論の確認であり、執筆の承認ではない。後の段階で前の段階の結論と矛盾が見つかった場合は、該当する段階に戻って詰め直す。

ユーザーが決まっていない、わからないと答えた項目は、考えさせ続けずに `TBD` として次へ進む。

### 4. 材料一覧を提示して合意を取る

三段階を終えたら、全8項目を段階ごとに一覧で示す。各項目に根拠の種類（コードで確認、ユーザー回答、`TBD`）を併記し、`TBD` の件数を添える。この内容で PRD を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順5へ進む。

### 5. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料を渡して PRD を執筆させる。材料には、リポジトリのコード、ファイル、コミットへの参照と、実現方式（how）を含めない。

PRD の保存先ディレクトリはリポジトリごとに一つに固定し、リポジトリルートの `AGENTS.md` の「PRD の保存先」に記す。記載があればそのディレクトリに保存し、ユーザーに問わない。記載がなければ、保存先をユーザーに確認し（推奨は `docs/prd/`）、`AGENTS.md` に「PRD の保存先」として追記してから保存する。`AGENTS.md` がなければ作成する。保存先は tanteki にも渡す。

PRD のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存 PRD の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは PRD の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_environment-setup.md`

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- 実装の構成、データの流れ、技術選定の記録（Design Doc、ADR の領分）
- 見つかったバグの修正、リファクタリング
- 作業の分担と進捗（計画、チケットの領分）
