# code-to-adr: コードからのADR逆生成スキル

ADR の材料を grilling で三段階に分けて詰め、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

## 手順

### 1. 記録する決定を一つに絞る

ADR にする決定と、その決定を実装しているディレクトリ、エントリポイント、設定のいずれかをユーザーに確認する。複数の決定が混ざっている場合は、どれを記録するかをユーザーに選ばせる。リポジトリ全体の技術選定を一つの ADR にしない。

対象を決めた時点のコミットを記録し、以降の調査はこのコミットを基準にする。

リポジトリルートの `docs/prd/` と `docs/adr/` に、この決定の上位にある PRD や関連する ADR があれば読む。PRD の要求は、手順3で背景と制約の手がかりにする。既存の決定を変える場合は旧 ADR を書き換えず、新しい ADR から旧 ADR を参照する。

### 2. 読者を確認する

ADR の読者は技術責任者、開発者、将来の保守者である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 3. grilling を三段階で行う

9項目を次の三段階に分け、段階ごとに `Skill` ツールで `grilling` を呼ぶ。後の段階は前の段階の結論に依存するため、段階の順序を入れ替えず、前の段階が確定するまで次の段階へ進まない。

| 段階 | 狙い | # | 項目 | 主な手がかり |
|---|---|---|---|---|
| 1. 決定 | 何を選んだかを定める | 1 | 決定 | コード、設定、ドキュメント |
| | | 2 | 背景 | PRD、ドキュメント、コミット履歴 |
| | | 3 | 制約 | PRD、ドキュメント |
| 2. 理由 | なぜ選んだかを定める | 4 | 決定理由 | PRD、ユーザー回答 |
| | | 5 | 代替案 | ユーザー回答 |
| 3. 記録 | 採用の影響と記録を定める | 6 | 結果 | コード、設定、ドキュメント |
| | | 7 | 決定の状態 | ユーザー回答 |
| | | 8 | 決定日 | ユーザー回答、コミット履歴 |
| | | 9 | 出典 | PRD、ADR、ユーザー回答 |

各段階の grilling には、その段階の項目、手順1で決めた対象、前の段階で確定した結論を渡す。

grilling は、環境を調べてわかる事実は調べて埋め、決定はユーザーに委ねる。このスキルでは、この区別を次のように当てはめる。

- 事実: 決定がコードでどう実装されているか、採用によって何が必要になり、何が手作業として残るか。対象のコード、設定、テスト、ドキュメント、履歴を読んで埋める。根拠のファイルと行番号は材料一覧で示すが、ADR には含めない。
- 決定: なぜその案を選んだか、どの代替案と比べてなぜ採らなかったか、いつ決めたか。コードから推測できても事実として扱わず、推奨回答としてユーザーに問う。

ADR は現状の仕様に反してはならない。ユーザーの回答やスキルの推奨回答がコードの振る舞いと食い違う場合は、その食い違いを示してユーザーに確かめる。例えば OS ごとに異なる仕組みを使っているのに、共通の仕組みとして書かない。

ADR はコードより上位の文書であり、コードが ADR に従う。ADR からリポジトリのコード、ファイル、コミットを参照しない。材料には次を含めない。

- ファイル名、ディレクトリ名、パス
- 関数名、変数名、設定の出力名、命名規則などの実装の詳細

これらは「導入スクリプト」「共通の設定」「ロックファイル」のように、役割を表す語に言い換える。ツール名やフレームワーク名は、決定の対象そのものであれば含めてよい。

制約の各項目が、決定または決定理由のどれに対応するかを確かめる。対応する記述がない制約は、決定か決定理由に加えるか、制約から外すかをユーザーに問う。

代替案の不採用理由は、背景と制約に照らして述べる。推奨回答として不採用理由を示す場合も、ユーザーが承認するまで材料に書き込まない。

決定日は、コミット履歴から読める導入日と異なってもよい。履歴の日付を示したうえで、ユーザーに選ばせる。

決定の状態は「提案」「採用」「廃止」「置換」から選ばせる。実装済みの決定でも、状態は推測で決めない。実装の進捗である「未着手」「作業中」「完了」を状態として受け取らない。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。コードとユーザーの回答のどちらにもない事実、数値、条件を補わない。

段階の終わりに、その段階の結論を短くまとめて示し、修正がないことを確かめてから次の段階へ進む。これは段階の結論の確認であり、執筆の承認ではない。後の段階で前の段階の結論と矛盾が見つかった場合は、該当する段階に戻って詰め直す。

ユーザーが決まっていない、わからないと答えた項目は、考えさせ続けずに `TBD` として次へ進む。ただし「決定」が `TBD` のままでは ADR が成立しないため、決定が定まるまで手順4へ進まない。

### 4. 材料一覧を提示して合意を取る

三段階を終えたら、全9項目を段階ごとに一覧で示す。各項目に根拠の種類（コードで確認、PRD、ユーザー回答、`TBD`）を併記し、`TBD` の件数を添える。この内容で ADR を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順5へ進む。

### 5. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料を渡して ADR を執筆させる。材料には、リポジトリのコード、ファイル、コミットへの参照を含めない。出典には PRD、ADR、ユーザーへのヒアリングだけを挙げる。

ADR の保存先は、どのリポジトリでもリポジトリルートの `docs/adr/` に固定する。保存先をユーザーに問わず、tanteki にも渡す。

ADR のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存 ADR の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは ADR の決定内容を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_manage-environment-with-nix-flakes.md`

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- 実現方法の構成やデータの流れ（Design Doc の領分）
- 見つかったバグの修正、リファクタリング
- 作業の進捗、PR 番号、課題ID（チケット、進捗文書の領分）
