# create-adr: ADR作成ヒアリングスキル

ADR の材料を grilling で聞き取り、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

## 手順

### 1. 資料を確認する

ユーザーが示した資料と、これまでの会話だけを読む。リポジトリを自発的に探索しない。既存の記述から埋まる項目は、手順4で飛ばす。

### 2. 記録する決定を1つに絞る

ADR は一つの決定を記録する。複数の決定が混ざっている場合は、どれを記録するかをユーザーに選ばせる。

既存の決定を変える依頼であっても、旧 ADR を書き換えない。新しい ADR を作り、置き換える旧 ADR への参照を材料に含める。

### 3. 読者を確認する

ADR の読者は技術責任者、開発者、将来の保守者である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 4. grilling で9項目を詰める

`Skill` ツールで `grilling` を呼び、次の9項目を論点として順に詰める。手順1で埋まっている項目は飛ばし、飛ばしたことをユーザーに伝える。

| # | 項目 | 何のために聞くか |
|---|---|---|
| 1 | 背景 | 決定が必要になった状況を示す |
| 2 | 制約 | 選べる案を限る条件を示す |
| 3 | 決定 | 何を選んだかを定める |
| 4 | 決定理由 | 背景と制約から決定を導く |
| 5 | 代替案 | なぜ他の案を採らないかを示す |
| 6 | 結果 | 採用で何が変わり、何を引き受けるか |
| 7 | 決定の状態 | 提案、採用、廃止、置換を区別する |
| 8 | 決定日 | いつの決定かを残す |
| 9 | 出典 | 各主張の根拠となる原資料 |

9項目はいずれもユーザーが決めることであり、調べて埋める事実ではない。grilling が求める環境の調査は手順1の範囲にとどめる。

grilling が求める推奨回答は、提案であることを明示して示す。ユーザーが承認するまで材料に書き込まない。回答にない事実、数値、条件を補わない。

決定の状態は「提案」「採用」「廃止」「置換」から選ばせる。実装の進捗である「未着手」「作業中」「完了」を状態として受け取らない。

ユーザーが決まっていないと答えた項目は、考えさせ続けずに `TBD` として次へ進む。ただし「決定」が `TBD` のままでは ADR が成立しないため、決定が定まるまで手順6へ進まない。状態が「採用」の場合は、採否を左右する未確認事項も `TBD` として残し、消さない。

### 5. 材料一覧を提示して合意を取る

grilling の最終確認として、全9項目を一覧で示し、`TBD` の件数を併記する。この内容で ADR を書いてよいか確認し、承認を待つ。承認を二度に分けず、ここで得た承認をもって手順6へ進む。

### 6. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料を渡して ADR を執筆させる。

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- ADR ファイルの保存先と採番
- 実現方法の構成やデータの流れ（Design Doc の領分）
- 後続の詳細設計に残る TODO（設計書、作業文書の領分）
- 作業の進捗、PR 番号、課題ID（チケット、進捗文書の領分）
