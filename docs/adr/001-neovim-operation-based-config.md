# ADR 001: Neovim 設定を操作単位で定義する

- 状態: 採用
- 決定日: 2026-09-24
- 出典: 2026-09-24 の聞き取り。置き換える旧 ADR はない。

Neovim の設定を、プラグイン単位ではなく操作単位のモジュールに分割する。キーマップと役割を操作名からたどれるようにするためである。

## 背景

Neovim の設定はプラグイン単位のファイルに分かれている。プラグインが増えるにつれてキーマップの全体像が把握できなくなった。設定も肥大化し、どのファイルが何の役割を担っているのか分からない。

## 制約

- プラグインは使い続ける。分割の軸に使わないだけで、標準機能への置き換えは意図しない。
- 既存のキーマップは維持する。
- Lua で書き、luacheck、stylua、busted の検査を通す。

## 決定

設定の分割単位を、プラグインから操作へ変える。操作は「ファイルを開く」「シンボルを検索する」「定義へ移動する」「差分を見る」のような、動詞ベースの細かい単位とする。

操作ごとにモジュールを1つ置き、その操作のキーマップ、オプション、プラグイン宣言をモジュール内にまとめる。プラグイン名は設定の構造に現れず、操作モジュールの内側に閉じる。

## 決定理由

キーマップの全体像が把握できないのは、キーマップがプラグイン単位のファイルへ散っているためである。操作を単位にすれば、あるキーマップを探す先は操作名で決まる。どのファイルが何の役割を担っているか分からないのは、ファイル名がプラグイン名であって役割を表していないためである。ファイル名を操作名にすれば、役割はファイル名から読める。

プラグインを使い続ける制約のもとでも、プラグイン宣言を操作モジュールの内側に閉じれば、プラグインの乗り換えは該当するモジュール1つの書き換えに収まり、設定の構造は動かない。あわせて、キーマップ宣言を値として持てるため、割り当ての重複や欠落をテストできる。操作のロジックも副作用から切り離せば、そのままテストできる。

## 代替案

- 現状維持（プラグイン単位のまま）。キーマップの所在がプラグインの知識に依存し続けるため、背景の問題が残る。
- キーマップのみ1ファイルへ集約し、他はプラグイン単位のままとする。一覧性は得られるが、キーマップと実装が離れるため役割は読めないままで、二重管理になる。
- レイヤ単位で分ける（core、ui、lsp、git など）。プラグイン名は構造から消えるが、粒度が粗く、どの操作がどこにあるかがレイヤの知識に依存する。
- プラグインを減らし、標準機能中心に書き直す。設定量は減るが、プラグインを使い続ける制約に反し、操作の把握という問題とは軸が異なる。

## 結果

1つのプラグインが複数の操作に跨る場合、その初期化と設定をどこへ置くかの判断が毎回発生する。プラグイン単位ではこの判断は不要だった。具体的な置き方は後続の設計で決め、この ADR では扱わない。

オプション、配色、クリップボードなど、操作に属さない設定の置き場所を別に設ける必要がある。
